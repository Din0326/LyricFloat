# 桌面懸浮歌詞 產品規格書 v1.84

## 文件資訊

本文件定義一個以繁體中文與英文歌詞為主的桌面懸浮歌詞工具，第一版鎖定 Windows，以 PyQt6 實作。

修訂紀錄：v1.82 L3 判斷語言不看開頭的製作資訊（Din 選擇重做舊結果）：網易雲歌詞開頭常有「作词 : 某人」「作曲 : 某人」「编曲 : 某人」等製作資訊行，原本判斷語言時整份歌詞只要有漢字就當華語，英文歌因此以華語做開唱點搜尋與整首 L3 對時（連帶做 t2s 轉換）。實測「Pillows — eaJ x keshi」（Chrome 影片，網易雲 1501413336，2026-10-12）兩次開唱點搜尋都記為華語、都沒找到。改為從第一句有唱的歌詞起判斷（略過規則同 v1.29 對齊開唱的第一句：開頭的製作資訊與沒有字母、數字的行）；第一句之後的「男：」「女：」等對唱標記照舊算，整首都有這類標記時看全部行。升級時（快取 v9）找出語言因此改變的歌，清除其 L3 結果與失敗次數（已採用、不採用、放棄、失敗都清），下次完整播放重新對時；使用者還原過原始時間軸的歌維持不再校正。

修訂紀錄：v1.83 全大寫縮寫的歌手名可由影片標題裡的全名對上（Din 同意）：PG One 頻道的「Fast-Track Pathway - "BOOM一下你就BAP" (Lyric Video)」找不到歌詞，兩個來源其實都回傳了〈Boom一下你就Bap〉，但歌手寫的是縮寫「FTP」（網易雲「FTP / 杀手耗 / Dracooo / OB03」），v1.58／v1.61 要求歌手相同或出現在標題、頻道中，因而被擋下（2026-10-08 這兩條規則之前找得到）。候選歌手中 3～6 個大寫字母的名字，若影片標題或頻道名中有連在一起（只隔空格或連字號）的幾個英文字、字首字母剛好拼出它，就算同一位歌手，影片辨識的確認與一般查詢的歌手條件都適用；2 個字母（例：ET）任兩個字都可能湊出，不算。修正後採用網易雲同步版；Din 的 44 個 Chrome 影片結果不變。

修訂紀錄：v1.84 L3 只用 CPU、維持 Whisper base（Din 選擇，覆蓋 v1.3「偵測到 CUDA 時改用 GPU」）：這條自 v1.3 起寫在規格裡、從未實作，v1.22 起 L3 依 CPU 實作，執行環境下載的也是 PyPI 的 CPU 版 PyTorch。依據 Din 另一台機器的實測（2026-10-19，RTX 4080 SUPER 16 GB、i9-12900KF；8 首歌：華語 2、英文 2、日語 1、饒舌 1、粵語 1、長前奏 1，每首錄一次、同一份錄音跑 5 組；量測腳本 `tools/l3_gpu_bench/` 只留在那台、未納入版控）：同一個模型改用 GPU 只變快、不變準——base 在 CPU（int8）與 GPU（float16）都是 8 首全採用，0.3 秒內 0.84／0.85、與 LRC 的中位絕對差 0.166／0.162 秒；每首處理平均 110 秒降為 6 秒（約 17 倍），但整首對時在背景執行、結果下次播放才用，使用者看不出差別。代價：執行環境多下載約 2.5 GB（CUDA 版 PyTorch 2604 MB，CPU 版 124 MB）；須固定 cu126 版（ctranslate2 4.8.2 需要 cuBLAS 12，cu130 版附的是 cuBLAS 13），系統 PATH 上的 CUDA Toolkit 會被優先載入；記憶體較高（人聲分離 private commit 4.9 GB，CPU 3.5 GB）；開發機沒有 NVIDIA 顯示卡，無法驗證。較大的模型也沒有更準：small 0.3 秒內 0.83（英文 0.75，base 0.78），CPU 上對齊多約 11 秒；medium 降到 0.58，多首整體偏晚 0.2–0.3 秒。另更正「執行」的開發機耗時：原記 40–60 秒是依 v1.22 可行性驗證推估（驗證工具預設用一半的執行緒，即 8 個）；正式版 4 個執行緒、最低優先權，開發機 149 首（2026-10-07～10-12）中位 77.5 秒（10%–90%：58–100 秒；錄音長度中位 220 秒），人聲分離每秒音訊 0.31 秒（另一台 i9-12900KF 以一般優先權為 0.34–0.46 秒）。

## 產品概述與目標

LyricFloat 讓使用者在任何播放器聽歌時，都能在桌面上看到同步、繁體或英文的懸浮歌詞，不必切回播放器。

現有工具的三個問題：

- 歌詞來源以酷狗、網易雲為主，台灣華語歌常顯示簡體字與中國用語。
- 英文歌匹配率依賴中文歌詞庫，冷門或新歌常找不到。
- 綁定單一播放器（多為 Spotify），還需要申請開發者應用與 OAuth。

產品定位：播放器無關、繁體優先、英文友善、開箱即用的桌面歌詞工具；定位為個人使用，不公開發布。

| 成功指標 | 目標值（v1.0 發布時） |
| --- | --- |
| 英文歌同步歌詞命中率（以 200 首測試歌單計） | ≥ 85% |
| 台灣華語歌同步歌詞命中率 | ≥ 75% |
| 時間軸誤差：抽樣行開始時間與人工標註相比的中位數 | ≤ 500 毫秒（v1.1 起 ≤ 300 毫秒） |
| 顯示內容殘留簡體字比例 | 0%（全部經過轉換） |
| 從切歌到顯示第一行歌詞 | ≤ 1.5 秒（快取命中 ≤ 200 毫秒） |
| 首次安裝到看到歌詞的步驟數 | ≤ 2 步，無需任何金鑰 |

## 目標使用者與使用情境

主要使用者是在台灣、習慣邊工作邊聽歌的桌機使用者，聽的歌以英文與華語為主。

| Persona | 描述 | 核心需求 |
| --- | --- | --- |
| 工作中的工程師 | 雙螢幕，全天開 Spotify 或 YouTube Music | 歌詞不擋程式碼、滑鼠可穿透、低資源佔用 |
| 英文學習者 | 用英文歌練聽力 | 英文原文搭配繁中翻譯雙行顯示 |
| 華語歌迷 | 聽台灣流行樂，用 Spotify 或 YouTube Music | 歌詞是正確的繁體、卡拉 OK 逐字效果 |
| 直播主 | 直播時想在畫面上顯示歌詞 | 可自訂樣式、綠幕背景或可被 OBS 擷取的視窗 |

核心情境：

1. 使用者開啟任一播放器播歌，LyricFloat 自動偵測歌曲並顯示同步歌詞。
2. 使用者鎖定歌詞視窗，滑鼠穿透到下方應用程式，繼續工作。
3. 歌詞錯誤或不同步時，使用者手動搜尋替代版本或調整偏移。
4. 英文歌時顯示原文加繁中翻譯，華語歌時只顯示原文。

MVP 只做 Windows 上的「偵測 → 取歌詞 → 顯示」閉環，其他功能全部往後排。

| 階段 | 包含內容 |
| --- | --- |

| v1.1 | 卡拉 OK 填色（整行插值）、手動搜尋與挑選版本、全域快捷鍵、播放控制、釘選播放器（v1.19：Spotify 歌詞來源暫緩，L2 移到 v1.2） |
| v1.2 | 直向顯示、歌詞編輯器、主題匯入匯出、OBS 友善模式、背景強制對齊（L3）與逐字時間軸（v1.21：上傳 LRCLIB 移出範圍；v1.24：L2 不做） |

明確不做：

- 簡體中文介面與簡體歌詞顯示選項。
- 自建音樂播放器；本產品只讀取其他播放器的狀態。
- 手機版（iOS、Android）。
- 歌詞分享、社群、帳號系統。
- 日文、韓文歌的羅馬拼音或翻譯（可顯示原文，但不做特別優化）。
- 自動更新機制；個人使用以手動更新即可。

查詢順序：

1. 英文歌：快取 → LRCLIB → Spotify → 網易雲。
2. 華語歌（歌名或歌手含中文字元）：快取 → Spotify → LRCLIB → 網易雲 → 酷狗。
3. 英文歌的繁中翻譯是獨立查詢：主歌詞不論來自哪裡，都另向網易雲取翻譯行，依時間戳對齊：時間差 ≤ 1 秒，且網易雲的原文行與主歌詞行文字相似度 ≥ 0.8 才配對；對不上的行不顯示翻譯。

匹配規則：

- 正規化歌名：全半形統一（NFKC），英文轉小寫，去除 feat. 段落與版本說明。版本說明的邊界如下：
  - 括號內容一律去除，括號指 `()`、`[]`、`{}` 與全形 `（）`、`【】`、`［］`、`〔〕`；書名號與引號（`《》`、`「」`、`『』`）視為歌名本身，不去除。
  - 破折號只處理前後有空白的「 - 」（含 – —），且後段含版本關鍵字（Remaster、Live、Version、Edit、Mix、Mono、Stereo、Acoustic、Demo、Instrumental、版 等；v1.30 加上 YouTube 影片標題常見的 Video、MV、M/V、Audio、Visualizer，例：AIYOU - Eve Music Video）才去除，避免誤刪 Anti-Hero 這類歌名本身的連字號。
  - Remastered、Live 等關鍵字只在括號或破折號段落中去除，不刪歌名本文（例：Live Forever）。
  - 去除後若為空字串，保留去除前的字串。
  - 語言版本（v1.70）：Japanese／English／Chinese／Korean 等 Version 與 日文版、國語版 等雖在版本說明中去除，但候選寫了、播放器歌名沒寫同一種語言時，不採用該候選（歌詞是另一種語言）。
- YouTube 影片標題（v1.31）：Chrome 的 YouTube 回報的是影片標題，常把歌手放在前面或把歌名放在【】內。查詢來源與評分前先取出歌名（v1.54：瀏覽器的歌手欄先去掉結尾的「 - Topic」、「VEVO」、「 Official」「 Official Channel」、「官方頻道」，頻道名就是歌手）：以破折號切開（v1.37：一側有空白即可，例：「王水源 Lifloo -【保持呼吸】」；兩側都沒空白的連字號如 Anti-Hero 不切）後，去掉正規化後等於歌手名（含拆開的多位歌手）、歌手名加至多兩個英文字的別名（v1.37，例：王水源 Lifloo）、或拆開後含有歌手名的段落（v1.32：影片標題另以前後有空白的字母 x 拆開，例：張瑚HU X 趙翊帆YI94；快取鍵用的歌手拆法不變）；若剩下的內容去掉歌手名與影片用語（Music Video、Lyric Video 整詞（v1.37）、Video、MV、M/V、Audio、Visualizer、Official）後已無文字，改取第一個【】或 [] 內有內容的文字。都不符合時維持原標題。快取鍵與畫面顯示仍用播放器回報的標題；手動搜尋視窗預填取出的歌名（v1.76：已找到歌詞時預填找到的版本；v1.77：否則預填完整影片標題、歌手留空，見 FR-12）。v1.33：被去掉的歌手段落中、播放器歌手以外的歌手也納入歌手比對（查詢仍以播放器回報的歌手為第一位）。v1.66：取出的歌名只剩一段時，結尾、括號外的影片用語（Official、Music Video、Lyric Video、Video、MV、M/V、Audio、Visualizer）去掉，去掉後仍有文字才採用（例：「BIGBANG - HARU HARU(하루하루) M/V」取「HARU HARU(하루하루)」）；還有兩段以上時不去，結尾的影片用語讓正規化把那段當版本說明去掉。v1.66：瀏覽器影片的標題恰好以破折號分成兩段、兩段都不是頻道的歌手、前段有文字，且頻道名（或其中文、英文部分，英文須是完整的字）沒有出現在後段時（頻道是唱片公司或歌詞頻道，例：BROYA ICEBOX 上傳「FRαNKIE阿法 - 沒有妳在 Not Around ft.王ADEN (Dir.by @VincentWan9)」），以前段為歌手（查詢的第一位，頻道名排第二、仍納入歌手比對）、後段依上述規則取出歌名；後段緊接文字的「ft.」「feat.」先補上空格。後段沒有歌名時不適用。「歌名 - 歌手」順序的標題這樣查不到，照舊交給影片辨識。
- 瀏覽器影片辨識（v1.34）：只用於瀏覽器（Chrome、Edge、Firefox 等）的會話。
  - 長度超過 15 分鐘的影片，或沒有回報歌手（v1.43：抖音、Instagram 等其他網站；YouTube 與 YouTube Music 一律回報頻道名）的影片，視為不是歌（直播、vlog、短片）：不查詢、不寫快取、視窗留白。
  - 一般查詢的歌手條件（v1.58）：瀏覽器影片的歌手欄是頻道名，常是歌詞頻道，只靠歌名與長度會採用翻唱或別人的同名歌。一般查詢（含長度不同的版本）的候選，要是同一位歌手（v1.61：相似度 ≥ 0.8，或一個名字包含另一個），或候選的任一位歌手出現在影片標題或頻道名中，才採用；否則交給下面的影片辨識。
  - 以上規則（含長度不同的版本）都找不到、且至少有一個來源有回應時，把影片標題整理成最多 4 個全文查詢（v1.40；原為 3 個）：《》內的文字（v1.40，優先；v1.41：先於雜訊處理取出，# 號去掉）、單引號歌名連同前面的歌手（v1.46，K-pop：歌手 '歌名'）、【】內的文字（v1.67）、括號外的文字（v1.42：依「|」切段，每段各自查詢；v1.46：「│」也切；v1.60：前後有空白的「 / 」也切）、【】『』「」[]()與引號內的文字、全部文字；先去掉 Official、Music Video、Lyrics Video、Audio、MV、Prod. 製作人、動態歌詞、中文歌詞、#標籤、畫質（1080P、60fps、60帧、4K、高清、超清、藍光，v1.40）、電視打歌舞台（v1.52：@帳號、播出日期、EP 集數、電視台、節目名、방송；v1.60：THE FIRST TAKE）、節目的「纯享」（v1.67）、歌詞付き（v1.52）等用語，中文與英文相接處補空格（v1.38；v1.55：另以不補空格的寫法再查一次）。簡體的查詢送往非簡體來源（LRCLIB）時，另以繁體（只轉字）再查一次（v1.40）；繁體的查詢另以簡體再查一次（v1.56）；以中文歌名開頭、後接英文的查詢，另以該中文段再查一次（v1.69）。單引號只在前後有空白時算引號（K-pop 標題，例：MARK 마크 'Flight to NYC'），避免把 Don't 拆開。
  - 依來源順序以各來源的全文搜尋查詢（LRCLIB 的 q 參數、網易雲 cloudsearch），候選必須同時符合：歌名（正規化後至少 2 字；v1.57：只有一個字時須是影片標題中獨立的一段；v1.68：雙語歌名的中文段或英文段也算）與任一位歌手（至少 2 字；v1.47：歌手欄括號內的名字也算，例「丽兹（LIZ）」算丽兹與 LIZ，純數字不算；v1.48：中文名與英文名相連的也拆開算，例「弹壳Danko」算弹壳與 Danko；v1.53：歌名不可落在完整歌手名之內，「ICE杨长青」的 ICE 不算歌名，v1.67：括號內的別名也算完整歌手名；v1.59：名字前後的符號不算，中英交界夾著符號也拆開，例「NINEONE#乃万」；v1.71：夾著空格也拆開，例「TANK 呂建忠」；v1.83：3～6 個大寫字母的名字可由標題裡連在一起的字首字母對上，例 FTP＝Fast-Track Pathway）都出現在影片標題或歌手欄中，且兩者是不重疊的兩段文字（例：「thomeboydontkill — THOME」不算，THOME 在歌名那段裡面）；比對前兩邊統一為簡體（v1.51：逐段轉換漢字，含假名或韓文的標題也轉）、去空白、「妳」視同「你」；影片比該版本短不超過 3 秒（v1.73：15 秒，唱片公司的 MV 常是剪短的版本）、長不超過 3 分鐘（MV）。
  - 通過確認的候選依序取歌詞（網易雲最多抓 3 筆），第一個有同步歌詞者採用，沒有才用純文字；長度差超過 3 秒者標記為長度不同的版本（見上），照對齊開唱規則顯示。不做 L1 比對。畫面與快取鍵仍用播放器回報的標題。
  - 以上都沒有確認的候選時（v1.35），以「歌手欄＋標題文字」再搜尋一次，用於標題只剩另一位歌手名的情況（例：歌名「OSN)」、歌手 Dizzy Dizzo 蔡詩芸）。候選的演出者必須同時含有歌手欄的歌手與這段文字（至少 2 字，且不是歌手欄歌手本身的名字），長度合理；符合的歌只能有一首（以正規化歌名區分），兩首以上視為無法判斷、不採用。
  - 辨識過程中的請求失敗不算「所有來源都失敗」（一般查詢已有回應）：顯示找不到歌詞、不記住，下次播放重查。
- 正規化歌手：規則同歌名，另依 `,`、`&`、`/`、`;`、`×`、`、`、feat.、ft. 拆成多位；比對時兩邊兩兩計算，取最高相似度。
- 雙語歌名（v1.10）：正規化後同時含中文段與拉丁字母段（兩段皆非空，且拉丁段含字母）時，歌名相似度取「全名／中文段／英文段」兩兩比對的最高值；來源（v1.32 起含網易雲：英文段可能讓同名的英文歌手淹沒結果）的精確查詢與搜尋都沒有通過門檻的候選時，改以中文段重查，評分仍以原歌名計算。純中文、純英文、或已被括號規則處理掉的歌名，行為不變。v1.66：中文段重查也沒有通過門檻的候選時，它找到的「只因時長被淘汰」且歌名等於中文段（相似度 ≥ 0.95）的版本，與全名查詢的結果一起納入長度不同的版本（原本只看全名查詢的結果）。
- 比對歌名時，播放器標題拆出的片段（雙語歌名的中文段或英文段）剛好等於歌手名者不當歌名比對（v1.37：「王水源 Lifloo」拆出的「王水源」曾以 0.86 配到〈愛王水源〉）。
- 比對歌名時「妳」一律視同「你」（v1.32：台灣用「妳」，網易雲等以「你」收錄，t2s 也不轉換「妳」）；只影響比對，快取鍵不變。
- 與簡體來源（網易雲）比對歌名前，兩邊先以 OpenCC t2s 統一為簡體（含假名或諺文的歌名除外），避免同一首歌因簡繁字形不同而相似度偏低。歌手別名（例：G.E.M.鄧紫棋 對 鄧紫棋）的包含比對不在此規則範圍內。
- 查詢簡體來源前，歌名與歌手先經 OpenCC t2s 轉換。
- 候選評分：歌名相似度 50%、歌手相似度 30%、時長差距 20%。時長分數 = 1 − |時長差| ÷ 3 秒（差 0 秒為 1、差 3 秒為 0），時長差超過 3 秒直接淘汰。「時長差 ≤ 2 秒優先」屬於 L1，見「自動時間軸校正」。
- 播放器未回報時長（時長為 0 或缺漏）時不做時長淘汰，權重改為歌名 5/8、歌手 3/8。
- 長度不同的版本（v1.29）：所有來源都沒有通過門檻的候選（同步、純文字、純音樂皆無）時（v1.62：瀏覽器影片只拿到純文字時也算，限比影片短的同步版；v1.63：採用的同步版歌名相似度 < 0.8 時也算，限歌名相似度 ≥ 0.95 的同步版；v1.75：採用的是標題沒寫現場的 Live 版時也算，限非 Live 版），才改用「只因時長差超過 3 秒被淘汰、且歌名與歌手以 5/8、3/8 重算仍達 0.7」的版本（v1.58：還要是同一位歌手，v1.61 起為相似度 ≥ 0.8 或一個名字包含另一個；瀏覽器影片另可由歌手名出現在影片標題或頻道名中代替），常見於 YouTube Music 播 MV（前後多了劇情）。依來源順序取第一個有同步歌詞者（v1.64：同一來源中分數相同者取長度最接近的），都沒有才取純文字；網易雲這類搜尋結果不含歌詞的來源，同樣最多抓 3 筆。結果標記為長度不同、不做 L1 比對，照常寫入快取（快取以時長 ±2 秒區分，MV 版與音訊版各自一筆）；查詢中有來源失敗時照樣顯示但不寫快取。手動綁定長度不同的版本也同樣標記。
  - v1.36、v1.79：同步版不論長度差多少，一律直接以來源時間軸逐行顯示（可能整首早或晚），工具列有「對齊開唱」，偏移鍵隨時可用；未對齊過的歌同時由開唱點搜尋在背景找開唱點（見「自動時間軸校正」的 L3 細則），找到就等同按了一次對齊開唱，整首歌詞一起移，閃現「已自動對齊開唱」（v1.80：與來源時間相差 2 秒內時不動、不存偏移、不閃現，等播完後的整首 L3 對時；整首對時照樣略過找到的開唱點前的前奏）；搜尋期間左上角標「自動對齊開唱中…」，可能的開唱範圍過了仍沒找到時閃現「沒聽到開唱點，可按 Ctrl+Alt+Down 對齊」，因暫停／拖動／關閉 L3 而停止時不提示。長度差超過 10 秒、一開始就沒有在聽（L3 未開、沒從頭播、換過播放器）時閃現「開唱時可按 Ctrl+Alt+Down 對齊」（v1.39）。同一首歌重新顯示（例如翻譯補上）時沿用這次播放的對齊結果。v1.79 覆蓋 v1.39「長度差超過 10 秒、搜尋進行中先停在第一句等待」。
  - 這次播放第一次按對齊開唱（且尚未自動對齊）時，按下的時間若落在第一句可能開唱的範圍（第一句來源時間加上 0 到長度差、前後各 3 秒）內，對齊第一句（略過開頭的作詞、作曲等「標籤：內容」行（v1.31：標籤最長 40 字，含中英雙語標籤）、「歌名 - 歌手」行與無文字的行）；否則同下方「對齊後再按一次」。使用者按過之後，晚到的自動結果不再套用。
  - 對齊後再按一次，畫面上的下一句從當下開始（歌手已唱到下一句、畫面還停在上一句時用）；1 秒內的第二次按下視為連按，不處理。歌詞超前（例如 MV 中段插入劇情）只能用偏移 −/+ 調整，或等 L3 校正。
  - 對齊的結果存為這首歌的偏移，下次播放直接同步；偏移上限（一般歌曲 ±30 秒）放寬為歌曲時長。
  - 純文字版照一般純文字規則等速捲動並標「未同步」，不提供對齊開唱。
  - 已知限制：英文 MV 若網易雲也只有長度不同的版本，沒有翻譯。
- 總分低於 0.7 視為未命中，繼續下一來源；通過門檻的候選中，有同步歌詞者一律優先於只有純文字者（不限同分）；同類中時長差 ≤ 2 秒者優先於 2–3 秒者（L1，含 2 秒），最後再比總分。播放器未回報時長時不分這一層；播放器有回報但候選本身沒有時長者，不列為優先。
- 只拿到純文字歌詞時先暫存，全部來源都沒有同步版本才以靜態捲動方式顯示：依歌曲時長等速捲動，並標示「未同步」。查詢中有來源連線失敗時，純文字與純音樂結果照樣顯示，但不寫入快取，下次播放重新查詢。
- 每個 HTTP 請求逾時 3 秒，同一來源的多次請求各自計時（例：LRCLIB 的 get 與 search 最長合計 6 秒）。連線在收到任何回應前中斷（伺服器斷線、連線被重設、連不上）時，該請求立即重送一次，重送仍計入同一個 3 秒；逾時與 HTTP 錯誤狀態碼不重送。例外（v1.65）：HTTP 503（伺服器忙碌）依回應的 Retry-After 等待（未指定為 1 秒）後重送一次，同樣計入同一個 3 秒；指定超過 1 秒或為日期時不重送；斷線重送後的 503 不再重送。快取與 LRCLIB 先查，未命中才依優先順序逐一查詢其餘來源，以降低對非公開端點的請求量。
- 查詢中有來源失敗（連線失敗或逾時）而找不到歌詞、或只拿到純文字或純音樂結果時，10 秒後在背景自動重查一次：仍在播同一首才查，每次播放最多一次；換歌、手動綁定或編輯歌詞即取消。重查結果與原本相同時不重畫畫面。
- LRCLIB 先以 `/api/get` 精確查詢（歌名、歌手，有值時帶專輯與時長），結果同樣經評分；未找到、低於門檻或只有純文字時，再以 `/api/search` 取候選清單評分。v1.33：帶歌手的搜尋沒有任何結果時，改以歌名單獨搜尋一次（LRCLIB 可能把歌登記在合唱的另一位歌手名下）；這些結果的歌手相似度未達 0.5 一律淘汰（手動搜尋標示「歌手不符」），其餘照一般規則評分。
- 對 LRCLIB 的請求帶上可識別的 User-Agent（產品名與版本）。

補充規則：

- 語言判斷分兩次：查詢前依歌名與歌手初判（先看假名或諺文，含有即判為其他；否則含漢字判為華語；其餘判為英文）；取得歌詞後依歌詞內容重判：先看假名與諺文，合計佔全部（漢字、英文單字、假名、諺文）10% 以上判為其他；否則漢字數多於英文單字數判為華語；其餘判為英文。若結果不同，改用正確的查詢順序重新評估候選。可處理英文歌名的華語歌與英文藝名的歌手。
- 解析 LRC 時讀取並套用 \[offset:\] 標籤。
- 快取以歌手＋歌名為鍵，時長以 ±2 秒容差比對，避免不同播放器回報的時長差異造成未命中。鍵中的歌名、歌手先經正規化與簡體偵測轉換（見「文字處理」）。快取不設容量上限；「找不到歌詞」只在本次執行期間記住，不寫入快取；查詢中有任一來源連線失敗時不記住，下次播放重新查詢（失敗的來源可能有這首）。
- 網易雲以 `/api/cloudsearch/pc` 搜尋、`/api/song/lyric` 取歌詞與翻譯，不帶任何帳號 cookie；舊的 `/api/search/get/web` 回傳已加密，不使用（v1.6 實測）。搜尋一次取前 30 筆：完全相符的版本可能排在 20 名之後（v1.12 實測）；取歌詞的請求數不因此增加。
- 評分權重（50/30/20）與 0.7 門檻為初始值；M1 先在日誌記錄每首歌的候選與分數，待 200 首測試歌單建立後校準並更新本節。

## 文字處理

所有中文文字在進入快取前就完成繁體轉換，顯示層只處理已經是繁體的文字。

| 時機 | OpenCC 設定 | 用途 |
| --- | --- | --- |
| 查詢簡體來源前 | t2s | 歌名、歌手轉簡體以提高搜尋命中 |
| 簡體來源回傳後 | s2twp | 逐行歌詞與翻譯轉台灣正體並替換慣用詞；含逐字時間的歌詞改用 s2tw 逐字轉換（只轉字、輸出台灣字形），避免字數改變造成時間錯位 |
| 非簡體來源回傳後（如 LRCLIB） | 逐行偵測 | 以行為單位套用簡體偵測規則，判為簡體的行依設定模式（預設 s2twp）轉換，其餘行原樣保留，避免誤改原本就正確的用字。LRCLIB 為社群資料，華語歌詞可能是簡體（v1.7 抽查：周杰倫〈晴天〉前 5 筆同步歌詞皆為簡體） |

規則細節：

- 網易雲與酷狗等簡體來源整份一律轉換；其他來源以行為單位偵測，偵測規則同下方歌名歌手的規則，判為簡體的行才轉換。
- s2twp 會替換詞彙（例：軟件→軟體），歌詞需要保留原詞時，使用者可在設定切成 s2tw（只轉字、不轉詞）。
- 提供自訂詞彙表，覆寫 OpenCC 的誤轉（例如歌手名、專有名詞）。
- 英文、日文假名、韓文不經轉換，原樣保留。
- 歌名、歌手來自播放器而非歌詞來源，無法依來源判斷；顯示與建立快取鍵前，偵測為簡體時才以 s2tw 轉換（只轉字、不換詞，避免改到專有名詞）。偵測方式：整串不含任何繁體專用字、且至少含一個簡體字，才視為簡體；兩份字元表由 OpenCC 資料預先產生（tools/gen_char_tables.py），偵測時不載入字典。只由兩岸通用字組成、靠詞組才能分辨的字串（例：皇后）會被判為簡體，但轉換後內容不變。只由兩岸通用字組成的字串（例：台北）會被轉為正式字形（臺北），可接受。
- Python 實作使用官方 OpenCC 套件（有 Windows 預編譯版，免編譯）；opencc-python-reimplemented 自 2023-02 未再更新，不採用。
- OpenCC 的 s2tw／s2twp 字典約 85 MB，只在轉換時載入（同一首歌的歌詞、翻譯、歌名共用一次載入），轉完即釋放，重新載入約 70 毫秒；t2s 字典約 4 MB，查詢網易雲與比對歌名常用，保持常駐。

中英混排：

- 字型由兩個欄位組成：西文字型（預設 Segoe UI）與中文字型（預設 Microsoft JhengHei，可選 Noto Sans TC），以 fallback 順序組合。
- 中文與英文、數字之間不自動插入空格，保留來源原樣。
- 單行超寬時先縮小字級至設定值的 80%，仍超寬則以跑馬燈捲動，不換行。

翻譯行：字級為主行的 75%，不透明度 80%，不做卡拉 OK 填色。

## 自動時間軸校正

歌詞時間軸不準時，系統依三層由便宜到精準自動校正，手動偏移只作為最後手段。

對不齊的主因有三種：版本不同造成的固定偏移（前奏長度不同）、整體速度差造成的線性漂移、以及製作者個別行標錯。

| 層級 | 方法 | 可修正 | 執行時機 | 版本 |
| --- | --- | --- | --- | --- |
| L1 中繼資料 | 優先挑選來源時長與播放時長差 ≤ 2 秒的候選；多來源都有時比對時間軸，剔除離群者；套用 LRC 的 \[offset:\] 標籤 | 版本錯配 | 查詢時 | MVP |
| L2 語音錨點 | 以 WASAPI 單一程序 loopback 只擷取播放器程序的音訊（不混入其他應用程式的聲音），取約 15 秒片段交給小型 Whisper 辨識，與歌詞模糊比對找出錨點；1 個錨點校正整體偏移，2 個以上做線性校正 | 固定偏移、速度差 | 首次播放、即時 | 不做（v1.24） |
| L3 強制對齊 | 播放期間錄下音訊，播完後背景以 Demucs 分離人聲，再以 stable-ts 或 WhisperX 將已知歌詞對齊到人聲 | 個別行錯誤；並產出逐字時間軸 | 首次播放後、背景 | v1.2 |

規則：

- 採用優先順序：使用者手動偏移或綁定 > L3 結果 > L2 結果 > 來源原始時間軸。例外（v1.29）：長度不同的版本，L3 結果優先於對齊開唱的偏移與手動綁定，因為兩者都只是在來源相對時間上的暫時對齊。
- L1 時間軸共識（v1.9，取代 v1.6 的英文歌限定規則）：主歌詞顯示後在背景進行，每首歌只檢查一次並記入快取。
  - 比對主要來源一次回傳的各同步版本；精確查詢命中、手上沒有其他版本時，另以該來源的搜尋取得（LRCLIB 為公開端點）。
  - 版本之間行開始時間的中位差超過 1 秒視為衝突，才查網易雲當第三票；英文歌本來就會查網易雲取翻譯，直接沿用。
  - 以 1 秒為容差分群：若有另一群至少 2 票，且票數多於目前採用版本所在的群，改用該群中評分最高的版本；票數不足時維持原本評分最高者。
  - 使用者已手動設定偏移的歌曲不自動換版本（手動優先）。查詢失敗時不記為已檢查，下次播放重試。
  - 換版本時歌詞會在播放中途重新定位，與翻譯行晚一步補上的方式相同。
- L2 錨點比對分數低於 0.7 時不套用；修正量上限為「候選時長與播放時長之差＋3 秒」，超過才視為歌詞匹配錯誤並觸發重新查詢，讓 MV 版較長前奏這類版本偏移仍可校正。
- L3 依歌詞文字判斷語言（有韓文為韓語、有假名為日語、有漢字為華語，否則英文），只看第一句有唱的歌詞起的行，開頭的製作資訊不算（v1.82）。
- L3 處理中文時，送對齊前以 OpenCC t2s 逐字轉換，對齊後依字元位置對應回原繁體文字；不得使用會換詞的 s2twp，否則字數變動會導致錯位。
- L2、L3 結果寫入快取並標記來源，之後播放直接使用。
- L3 細則（v1.22）：
  - 錄音：只在 L3 已啟用、該歌有同步歌詞、且沒有手動綁定、本地編輯版或手動偏移時錄；從歌曲前 15 秒內開始、途中沒有暫停或拖動、錄到結尾（至少涵蓋時長 85%）才算有效，否則捨棄、下次播放再錄。錄音寫入 `%LOCALAPPDATA%\LyricFloat` 下的暫存檔（不放在主程序記憶體，維持記憶體目標），對齊完成或放棄時立即刪除。
  - v1.28 錄音起點：Spotify 換歌當下的第一筆進度回報有時會提早約 0.5 秒宣告新歌已開始（實測兩次換歌中一次早 0.48 秒，下一筆 0.2 秒後即正確），只用這一筆會讓整首對齊結果偏晚（「走建國路回家但後座少ㄌ泥」偏晚約 0.6 秒，Din 以校對模式確認原始 LRC 準確）。起點改以錄音期間每筆回報各自推算的值取中位數；錄音比音訊早開始時起點為負數，不得截成 0。統計記錄起點修正量。升級時（快取 v7）清除所有已採用的對齊結果，下次完整播放時重做；原始時間軸不受影響，使用者還原過的歌維持不再校正。
  - v1.29 長度不同的版本：不論是否已對齊開唱（有偏移）或手動綁定都錄音；來源時間不可信，因此依純文字規則對時（不比較與原時間的差距）。對時被採用時偏移歸零（對齊結果已是絕對時間）；未被採用時保留對齊開唱的偏移。還原為原始時間軸後回到來源時間軸（v1.36：不再等待，可按對齊開唱）。
  - v1.36 開唱點搜尋：長度不同的同步版本在錄音時（尚未對齊開唱、沒有對齊結果）啟動（v1.74：所有同步歌詞在 L3 錄音時都啟動；長度相符的歌找到時只平移這次播放、不存成偏移，搜尋與沒找到都不提示；v1.80：找到的開唱點與來源時間相差 2 秒內時一律不動，原為長度相符的歌差不到 0.5 秒不動）。邊錄邊讀錄音檔（錄音檔改為無緩衝寫入），每 10 秒切一段、各帶前一段最後 2 秒，只處理可能含開唱點的片段（第一句來源時間加上 0 到長度差、前後各 3 秒；v1.44：到搜尋的最後一句為止）；交給模型常駐的工作程序（啟動後一次載入模型，每段約 5 秒）對齊前 5 句有字的歌詞（v1.44；原為 3 句），整段搜尋期間累積各段信心 0.3 以上、推算的偏移落在可能範圍內的句子，有 3 句不同的句子（只有兩句有字時為兩句）彼此相差 1 秒內即算找到（v1.44；v1.38 為前三句在同一段內全部達標，v1.36 為其中 2 句、信心 0.2），取中位數為偏移。工作程序落後 2 段以上時跳到最新一段。需要 L3 已啟用、執行環境就緒、可用記憶體 2 GB 以上；換歌、使用者按對齊開唱、暫停、拖動、關閉 L3 時停止。每次搜尋在統計記錄是否找到、偏移、處理段數與耗時，以及一致的句子與其信心、偏移（v1.44；沒找到時記最多的一組；只有數字）。粵語歌目前對不上（對齊以國語處理）。
  - v1.36 開唱點已知（找到或按過對齊開唱）的長度不同版本，整首對時從開唱點前 5 秒開始，略過前面的劇情與對白；統計記錄略過的秒數。
  - v1.26 純文字：來源只有純文字的歌、手動綁定的純文字版本、未對時的本地編輯版也錄音對時；有時間軸的手動綁定與本地編輯版照舊不錄。查詢時有來源失敗、沒寫進快取的純文字結果不錄（沒有可保存對齊結果的快取項目，下次查詢成功後再錄）。
  - v1.26 純文字的套用：沒有原時間可比，信心達門檻（0.2）的行即採用；整首有 6 成以上的有字行達標才採用，其餘行依前後已採用行的時間按順序內插，頭尾以已採用行的平均行距外推。對時後以同步歌詞顯示（拿掉「未同步」、可調偏移），並有逐字卡拉 OK。
  - v1.27 驗收（2026-10-07）：「语音备忘录 — PG One」（饒舌，只有 LRCLIB 純文字）完整播放一次後 59 行全數採用、平均信心 0.55，每行有逐字時間；Din 重播目視確認對上。
  - 執行：歌曲播完後排入佇列，子程序以最低優先權、最多 4 個執行緒處理；可用記憶體不足 3 GB 時延後。處理一首約 2–4 分鐘的歌，開發機（16 執行緒 CPU）約 60–100 秒（v1.84 更正，原記 40–60 秒）、記憶體峰值 1.5–2 GB。
  - 套用：中文先以 t2s 逐字轉換再對齊。只採用有把握的行——與原時間相差 3 秒內、且該行辨識信心達門檻；錄音涵蓋範圍內有把握的行不到 6 成時整份不用。沒被採用的行以有把握的行的中位差平移。
  - 逐字：採用的行附帶逐字時間，卡拉 OK 改為逐字填色；逐字時間來自畫面上的文字本身（對齊用的是它的 t2s 版本，依字元位置對回），因此不需改用 s2tw 顯示。字數對不上的行維持整行插值。
  - 每首歌記錄對齊統計（只有數字，不含歌詞）供調整門檻，華語精度以此補量。
- 套用自動校正後，停留工具列顯示「已自動校正」標記，可一鍵還原為原始時間軸。還原後該歌不再自動校正（FR-22）。
- 錨點只在預期時間前後 15 秒內的歌詞行中比對（預期時間先套用 L1 結果），避免重複的副歌比對到錯誤段落。
- 擷取到的音訊音量過低（例如使用者靜音）時跳過 L2、L3。

資源與隱私：

- L2、L3 在獨立子程序執行並使用 faster-whisper 等輕量推論引擎，不計入主程序的 CPU 與記憶體目標；L3 另限於歌曲播畢且系統閒置時以低優先權執行，可在設定關閉；只用 CPU（v1.84：不使用 GPU，覆蓋 v1.3「偵測到 CUDA 時改用 GPU」）。
- 錄下的音訊只存於本機暫存，對齊完成後立即刪除，不上傳。
- 模型在首次啟用該功能時才下載，不包含在安裝包內，維持安裝包 < 80 MB。
- v1.21（Din 決定）：免安裝版也支援 L2、L3。首次啟用時除了模型，也下載推論用的執行環境（Python 與 faster-whisper、PyTorch 等套件，數百 MB）到 `%LOCALAPPDATA%\LyricFloat`；只從官方來源（python.org、PyPI、模型發布處）下載，套件版本與雜湊值固定並驗證。

## UI/UX 設計規格

設計原則是「不打擾」：預設只有文字可見，所有控制項只在滑鼠停留時出現。

| 視窗狀態 | 外觀 | 滑鼠行為 | 進入方式 |
| --- | --- | --- | --- |
| 鎖定 | 只有歌詞文字，背景全透明 | 完全穿透 | 系統列或快捷鍵 |
| 解鎖－閒置 | 同鎖定 | 可點擊、不穿透 | 系統列或快捷鍵 |
| 解鎖－停留 | 半透明深色背景（不透明度 40%）＋工具列 | 拖曳移動、拖邊縮放 | 滑鼠移入 200 毫秒後淡入 |
| 隱藏 | 視窗不顯示 | 無 | 系統列或快捷鍵 |

佈局：

- 橫向雙行：第一行為當前句，第二行為翻譯；整首沒有翻譯（或已關閉翻譯）時第二行顯示下一句（字級 75%、不透明度 60%）；整首有翻譯但該行對不到翻譯時，該行單行顯示。
- 翻譯開關只影響顯示：英文歌一律查詢並快取翻譯，之後開啟開關不需再連網。
- 對齊方式可選：置中（預設）、靠左。左右交錯（類似網易雲桌面歌詞）不列入 MVP。
- 換句動畫（v1.81）：250 毫秒上推，先快後慢。第二行是下一句時，它往上移到第一行並放大成全尺寸，舊的一句往上淡出，新的下一句從下方淡入；第二行是翻譯或不是接著的下一句時，兩行一起往上滑一小段並交叉淡化，中間不出現空白。可關閉。

停留工具列（由左至右）：上一首、播放/暫停、下一首、偏移 −/+、對齊開唱（v1.29，只在長度不同的同步版本出現）、字級 −/+、鎖定、設定、關閉。MVP 只含偏移、字級、鎖定、設定、關閉。「關閉」為隱藏歌詞視窗，系統列圖示仍保留，可從系統列叫回。偏移按鈕的提示寫明「歌詞延後 0.1 秒」「歌詞提前 0.1 秒」，工具列顯示目前偏移值（例：+0.3s）。按住偏移按鈕可連續調整。

預設樣式：

| 屬性 | 預設值 |
| --- | --- |
| 主行字級 | 32 px |
| 未唱顏色 | #FFFFFF |
| 已唱顏色（卡拉 OK） | #4FC3F7 |
| 描邊 | 2 px、#000000、不透明度 70% |
| 陰影 | 模糊 6 px、偏移 0/2 px |
| 視窗位置 | 主螢幕底部置中、距工作列 80 px |

設定頁分為四個分頁：一般（開機啟動、語言、繁體轉換模式）、外觀（字型、顏色、即時預覽）、歌詞來源（啟用與排序、Spotify 憑證）、快捷鍵。介面語言規劃提供繁體中文與英文、預設跟隨系統；MVP 只提供繁體中文介面，Spotify 憑證與快捷鍵分頁隨 v1.1 功能加入。開機啟動以 Windows「啟動」資料夾捷徑實作，不寫登錄檔。MVP 的歌詞來源分頁只提供啟用與停用，查詢順序依「歌詞來源與匹配策略」的語言規則；排序功能隨 v1.1 的 Spotify、酷狗來源一併設計。

空狀態與錯誤：未偵測到播放時顯示「等待播放中…」後 3 秒淡出；找不到歌詞時顯示「歌名 — 歌手」與「找不到歌詞」；來源全部逾時時在系統列圖示顯示警示點，不彈視窗。

## 邊界情況與異常行為

原則是「寧可不顯示，也不顯示錯的」：無法確定時保持空白或停在當前行，不猜測。

| 情境 | 預期行為 |
| --- | --- |
| 多個播放器同時有媒體會話 | 跟隨 Windows 判定的目前會話；若它已暫停而另一個正在播放，改跟正在播放者。v1.49：只切換到播放中的會話；沒有播放時保留原本跟隨的會話，沒有可保留的就不跟隨（顯示「等待播放中…」，工具列播放鍵控制 Windows 目前會話）。可從系統列釘選特定播放器（FR-24） |
| 瀏覽器影片超過 15 分鐘或沒有歌手 | v1.34：超過 15 分鐘視為不是歌（直播、vlog、長片）；v1.43：沒有回報歌手（抖音、Instagram 等其他網站）同樣視為不是歌。不查詢、不寫快取、視窗留白 |
| Spotify 免費版廣告 | 僅套用於 Spotify 的會話：無專輯資訊且時長短於 60 秒視為疑似廣告，不查詢、不寫快取、視窗留白。Chrome 的 YouTube Music 在媒體會話中一律不回報專輯，套用會把短歌誤判為廣告，因此不套用 |
| 純音樂 | LRCLIB 標示 instrumental 時顯示「♪ 純音樂」，快取記錄以免重複查詢 |
| 切歌時前一首的查詢尚未完成 | 取消舊查詢與 L2 擷取，一律以最新歌曲為準，舊結果不得覆蓋顯示 |
| 單曲循環 | 進度由尾端跳回開頭時重置當前行，不重新查詢 |
| 使用者拖動進度 | 進度跳變超過 2 秒時以二分搜尋重新定位當前行，跳過換句動畫 |
| 暫停 | 停止推算進度，歌詞停在當前行；L2 擷取同步暫停；v1.45：連續 5 秒沒有播放時歌詞淡出（視窗與工具列保留），恢復播放即淡入 |
| 播放器關閉、會話消失 | 顯示「等待播放中…」後淡出 |
| 歌詞時間戳亂序、重複或一行多個時間戳 | 解析時展開為多行並依時間排序 |
| 系統睡眠後喚醒 | 重新取得媒體會話與進度，不沿用睡眠前的推算值 |
| 螢幕拔除或解析度變更 | 視窗位置超出可見範圍時移回主螢幕預設位置 |

日誌與問題回報：本機保留滾動日誌，記錄每首歌的候選來源、評分、採用結果與校正量。系統列提供「這首歌詞有誤」，將該筆紀錄與歌詞快照另存成檔，方便事後檢查，也可直接加入測試歌單。

| 編號 | 需求 | 優先級 | 驗收要點 |
| --- | --- | --- | --- |
| FR-24 | 從系統列釘選要跟隨的播放器 | P1 | 釘選後其他播放器的會話不影響顯示；依 App 識別碼釘選（同一播放器的多個分頁仍依多會話規則挑選），重開 App 後保留；釘選的播放器沒開時顯示「等待播放中」，選單標「（未開啟）」；v1.49：開著但還沒播放時同樣顯示「等待播放中」；選「自動」取消釘選 |
| FR-25 | 標記「這首歌詞有誤」並匯出診斷資料 | P0 | 產出含候選、評分與歌詞快照的檔案 |

## 風險與授權

最大的風險是非公開歌詞來源失效，因此核心體驗必須只靠 LRCLIB 與本地快取就能成立。

| 風險 | 影響 | 可能性 | 應對 |
| --- | --- | --- | --- |
| Spotify、網易雲、酷狗端點變更或封鎖 | 華語歌命中率下降 | 高 | 來源做成可插拔模組，失效時靜默停用並在設定頁標示 |
| 使用非公開 API 違反服務條款 | 發布管道受阻、法律風險 | 中 | Spotify 來源預設關閉、由使用者自行提供憑證；不內建任何憑證 |
| 歌詞著作權 | 公開發布時的法律風險 | 中 | 不重新散布歌詞、快取只存於本機、不提供匯出分享 |
| GPL-3.0 傳染 | 若複製參考專案程式碼，本專案需以 GPL 開源 | 低（可控） | 只參考架構與行為，所有程式碼自行撰寫 |
| PyQt6 授權 | PyQt6 為 GPL 或商業授權，閉源發布受限 | 中 | 個人使用不受影響；若日後公開發布再改用 PySide6（LGPL），兩者 API 幾乎相同 |
| OpenCC 誤轉 | 歌詞用字錯誤 | 中 | 自訂詞彙表、繁體來源不轉換 |
| 播放器未正確回報媒體會話進度 | 歌詞不同步 | 中 | 本地計時器推算進度，每次收到更新就校正 |
| 瀏覽器（Chrome）播放中不回報進度，只在暫停、播放、拖動時回報 | 中途緩衝卡住時歌詞跑在聲音前面，直到下次暫停或拖動才校正 | 中 | M2 評估長時間未收到回報時的處理方式 |
| LRCLIB 服務中斷 | 英文歌命中率下降 | 低 | 網易雲作備援、本地快取無上限保存 |

因定位為個人使用，授權與著作權相關風險影響有限；若日後改為公開發布，需重新評估本節。

## 驗收標準與測試策略

MVP 驗收以一份 200 首的固定測試歌單為基準：英文 100 首、台灣華語 80 首、其他 20 首，涵蓋熱門、冷門、Live 版、feat. 版與重新母帶版。歌單由 App 的播放紀錄整理出候選，再人工挑選補齊。

時間軸誤差以「校對模式」量測：聽歌時在實際開唱的瞬間按快捷鍵標記，與歌詞時間戳相減；抽 20 首、每首 5 行。

MVP 驗收清單：

- [ ] 英文歌同步命中率 ≥ 85%、華語歌 ≥ 75%；抽樣行時間軸誤差中位數 ≤ 500 毫秒
- [ ] 歌單全部顯示內容經自動掃描無簡體字
- [ ] Spotify、Chrome YouTube Music 兩個播放器切歌、暫停、拖曳進度皆正確同步
- [ ] 鎖定狀態滑鼠穿透、解鎖狀態可拖曳縮放
- [ ] 斷網時快取歌曲正常顯示、未快取歌曲顯示「找不到歌詞」
- [ ] 非功能需求表全部達標

| 測試層級 | 範圍 | 工具 |
| --- | --- | --- |
| 單元測試 | LRC 解析、歌名正規化、候選評分、OpenCC 轉換、翻譯行對齊、進度推算 | pytest |
| 契約測試 | 各來源回應格式，以錄製的回應重播，定期對真實端點備查；錄製檔中的歌詞文字以占位字串取代，版控中不保存真實歌詞 | pytest、vcrpy |
| 命中率回歸 | 200 首測試歌單批次查詢，產出命中率報告，低於門檻即失敗 | pytest、每週排程 CI |
| 標題變體自測（v1.50） | 播放紀錄中找到歌詞的歌套上 YouTube 常見標題格式，以瀏覽器影片重新解析，找不到與抓錯歌逐筆列出；改動影片辨識規則前後各跑一次 | tools/title_variants.py |
| UI 測試 | 視窗狀態切換、設定儲存與載入 | pytest-qt |
| 手動探索測試 | 多螢幕、高 DPI、全螢幕遊戲、長時間執行 | 測試清單 |

當前來源失效時，契約測試應在使用者回報前先失敗；契約測試失敗不阻擋發布，但要在版本說明標示該來源不可用。

## 里程碑規劃

開發分四個階段，每個階段以閘門條件放行，而不是以日期放行。

&#91;embedded content: 里程碑 · 4 個階段、3 個閘門\]

M1 閘門「原型可用」的判準：Spotify 與 Chrome 內的 YouTube Music 兩個播放器，以 `tools/measure_smtc.py` 量測的對時校正量 p95 ≤ 100 毫秒，對應非功能需求「歌詞時間誤差（相對播放器進度）≤ 100 毫秒」。對時校正量指每次收到播放器新回報時，App 當下顯示所依據的進度與新回報之間的差距。圖中「三播放器」改為上述兩個播放器，KKBOX 不在範圍內。

v1.15（Din 決定）：M2 的驗收清單（200 首命中率、時間軸校對、72 小時長跑、手動探索）與 v1.1 開發並行，不再等 MVP 驗收全過才開始 v1.1。v1.1 的閘門「命中率回歸不退步」仍需要 M2 的命中率基準報告。

v1.19 L2 可行性驗證（2026-10-07，`tools/l2_spike/`）：

- WASAPI 單一程序 loopback 在 Python（comtypes）可行，只錄到指定播放器；faster-whisper base（約 142 MB）載入約 1.5 秒，15 秒片段辨識通常 0.4 秒，偶爾 3–8 秒且佔用約 8 核，子程序 260–420 MB。
- 準確度（1 首華語、2 首韓文歌，共 19 個片段）：每 15 秒只辨識出 5–37 個字；最佳做法（以預期歌詞為提示、只比對預期位置前後 5 秒）8/10 片段有錨點，單一片段約一半落在 ±0.3 秒內，連續 3 片段取中位數約 ±0.25 秒，仍有重複副歌造成的離群值。
- 結論：L1 已處理 1 秒以上的版本錯配，L2 要補的 0.3–1 秒小偏移正落在它自己的誤差範圍，v1.1 做的價值不高；改與 L3 強制對齊一起在 v1.2 做，擷取程式沿用。
- v1.22：L2 改為把預期位置附近的已知歌詞強制對齊到 15 秒片段來找錨點（沿用 L3 的對齊程式），驗證後再決定是否實作。
- v1.24 驗證結果（`tools/l2_spike/align_run.py`，韓文、英文各 1 首）：8 個片段全部找到錨點、6 個落在中位數 ±0.3 秒內、1 個錯 1.5 秒；片段內各行估計差超過 1 秒的就是不可靠的片段。每片段約 10 秒（4 執行緒）。結論見 FR-20：不做。
